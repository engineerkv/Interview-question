# Agentic Workflows Cheatsheet

> **Reviewed:** 2026-09 · **Level:** Senior / Tech Lead · **Type:** Emerging

Quick review of the [Agentic Workflows](./index.md) section. Established principles are marked as such; everything else is emerging practice.

## Core definitions

- **Agent:** LLM + tools + loop + state, where the model chooses the next action. See [What Is an Agent](./foundations/01-what-is-an-agent.md).
- **Workflow:** LLM calls inside control flow you wrote. Prefer it when steps are known.
- **Harness:** deterministic code around the model that executes tools and enforces limits. Guarantees live here.
- **ReAct loop:** reason, act, observe, repeat. See [The Agent Loop](./foundations/02-agent-loop.md).
- **Autonomy:** grant per action, proportional to reversibility and blast radius.

## When to use an agent

| Use an agent when | Avoid or constrain when |
|---|---|
| Steps are not knowable in advance | You can draw the flowchart ahead of time |
| Success is verifiable (tests, schemas) | Success cannot be checked |
| Mistakes are reversible | Actions are irreversible or external |
| Latency of minutes is acceptable | Tight latency budget |

Error compounding: per-step success p over n steps gives roughly p to the power n.

## Tool design checklist

See [Tool Calling and Design](./tools-and-mcp/01-tool-calling-and-design.md).

- Verb-noun names; no overlapping tools.
- Descriptions say when to use, limits, formats.
- Strict JSON Schema; enums over free text; validate in harness anyway.
- Concise outputs with IDs for drill-down; paginate.
- Structured errors: code, message, retryable, hint.
- Idempotency keys generated by the harness (established).
- Least privilege, per-user scoped, short-lived credentials (established).
- Risk tier per tool: read, reversible write, irreversible or external.

## MCP in one breath

See [Model Context Protocol](./tools-and-mcp/02-model-context-protocol.md). Emerging, versioned spec.

- **Host** (app with model and policy), **client** (one connection), **server** (exposes capabilities).
- **Tools** (model-controlled), **resources** (app-controlled context), **prompts** (user-selected templates).
- **Transports:** stdio (local), Streamable HTTP (remote, OAuth-based auth).
- **Risks:** tool poisoning, changed definitions, cross-server injection, over-broad scopes. Vet, pin, sandbox, scope, confirm, log.

## Orchestration patterns

See [Workflow Patterns](./orchestration-patterns/01-workflow-patterns.md) and [Graphs, Retries, and Budgets](./orchestration-patterns/02-control-flow-and-budgets.md).

| Pattern | Use for | Watch out for |
|---|---|---|
| Prompt chaining | Fixed sequential steps with gates | Latency; errors flow downstream without gates |
| Routing | Specialized paths, cost control | Router is a single point of failure |
| Parallelization | Independent subtasks, voting | Aggregation, rate limits, correlated votes |
| Orchestrator-workers | Subtasks discovered at runtime | Budgets at both levels, worker status |
| Evaluator-optimizer | Clear criteria, verifiable output | Iteration cap, LLM judge blind spots |
| Planner-executor | Long tasks, reviewable plans | Plans without exploration, drift |
| Multi-agent | Context isolation, privilege separation | Cost, miscommunication, debugging |
| Graph / state machine | Explicit, checkpointable control flow | Over-granular graphs |

Retries: transport errors in harness with backoff; semantic errors to the model; validation failures retry with feedback and a cap.

Budgets: steps, tokens or dollars, wall clock, and side effects — enforced in code.

## Memory and state

See [Memory and Context](./memory-and-state/01-memory-and-context.md).

- Model is stateless; harness owns state.
- Context is a budget: summaries with handles, not raw dumps.
- Compaction: schema-based summary, pin constraints, archive raw history.
- Long-term memory: write policy, scope, provenance, expiry, deletion; beware memory poisoning.
- Checkpoint every step with versions and idempotency keys.
- Isolate state, sandbox, credentials, and memory per session and tenant.

## Evaluation

See [Evaluating Agents](./evaluation-and-reliability/01-evaluating-agents.md).

- **Outcome** (was the result right) and **trajectory** (was the path acceptable).
- Golden set from real tasks, frozen environments, grown from production failures.
- **pass@k:** at least one of k succeeds (capability, needs a verifier).
- **pass^k:** all k succeed (consistency, what unattended users experience).
- Multiple trials per task; gate on tolerance vs baseline; hard gate on safety.
- Simulate tools: record/replay, mocks with fault injection, sandboxes.

## Failure modes

See [Failure Modes Catalog](./evaluation-and-reliability/02-failure-modes.md).

| Failure | Mitigation |
|---|---|
| Loops | Repeat detector, step budget, re-plan |
| Tool hallucination | Strict schemas, reject unknown tools, check claims against trace |
| Wrong tool | Better names and descriptions, phase-based tool filtering |
| Partial completion | Checklist, verifier, status codes |
| Silent failure / false success | Harness derives status from evidence |
| Goal drift | Pin goal, final check against task |

## Human in the loop

See [Approvals and Escalation](./human-in-the-loop/01-approvals-and-escalation.md). Mostly established controls.

- Approval required for destructive, irreversible, costly, or external actions.
- Approve plans; bind execution to the plan; re-approve on deviation.
- Escalate on observable signals; self-reported confidence is often uncalibrated.
- Approval UX: exact action, evidence, blast radius, undo, expiry.
- Append-only, attributable audit log.
- Agent never approves itself; platform enforces separation of duties.
- Kill switch for write tools.

## Production and ops

See [Observability, Cost, Latency](./production-and-ops/01-observability-and-cost.md) and [Security, Rollout, Incidents](./production-and-ops/02-security-and-rollout.md).

- Trace: run span, step spans, nested model and tool spans with versions, tokens, cost.
- Key metrics: success, partial, and failed rates; cost per successful task; steps p95; tool error rate; approval rejection rate.
- Cost levers: workflows over agents, smaller models for easy steps, prompt caching, context trimming, parallelism, batch APIs.
- Rate limits per run, user, tenant, global; deduplicate during incidents.
- Sandbox agent code: isolation, no secrets, egress allowlist, resource limits.
- Prompt injection (especially indirect via tool outputs): no complete fix; privilege separation, approvals, egress control, output sanitization.
- Rollout: offline eval, shadow, assisted, canary, GA; kill switch.

## Applied scenario template

See [Engineering and Ops Agents](./applied-scenarios/01-engineering-and-ops-agents.md) and [System Design Questions](./applied-scenarios/02-system-design-questions.md).

For any scenario, state: goal, tools (and their risk tiers), loop, human gates, what NOT to trust the agent with, evaluation, and failure modes.

| Scenario | Autonomy | Human gate |
|---|---|---|
| Bottleneck analysis | Read-only | Human acts on report |
| Load-test generation | Sandbox and smoke run | Human reviews and runs real test |
| Incident triage copilot | Read-only plus post to incident channel | Commander owns decisions |
| Capacity-planning draft | Sandbox compute | Engineering and finance review |
| Code migration | Sandbox plus agent branch | Code review, human merge |
| Test generation | Sandbox | Review for intended behavior |

## Interview answer structure for agent designs

1. Clarify goal, users, and non-goals (what the agent must not do).
2. Decide workflow vs agent, and autonomy per action.
3. Sketch architecture: trigger, orchestrator, model gateway, tools, state, approval gate, tracing, audit.
4. Tools and permissions: least privilege, risk tiers, sandboxing.
5. Loop, budgets, and stop conditions.
6. Human gates and escalation.
7. Evaluation: golden set, outcome and trajectory, pass^k, shadow mode.
8. Failure modes, security (prompt injection), cost, and rollout.
